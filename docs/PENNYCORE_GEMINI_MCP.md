Public synthetic test endpoint: https://party.wildcarddev.com/api/pennycore-mcp-demo-v1

This endpoint is intentionally public, stateless, and unauthenticated. It has one fixed read-only tool, no imports in its implementation, no DB/network/env access, no private identifiers, no logging of arguments and no write methods. It cannot see the Owner memory bank, even when called with Party cookies or bearer credentials. Never add private functionality to this URL. It is not the private OAuth resource.

Google Connected Apps Platform currently supports MCP 2025-11-25 and earlier Streamable HTTP versions back to 2025-03-26, JSON text tool results, and GET 405 for stateless servers. See https://developers.google.com/connected-apps/mcp/server-optimization. The fixture supports those three versions, initialize, notifications, ping, tools/list and tools/call. No paid inference is made by the endpoint.

## Stage 2 prototype: separate authenticated fictional resource

Endpoint (not active until explicitly configured): `https://party.wildcarddev.com/api/pennycore-auth-demo`. Static, pre-registered public OAuth client `pennycore-gemini-demo-v1`, S256 PKCE, scope `pennycore.demo.read`, exact Google app-specific redirect allowlist, no client secret or refresh tokens. Manual client registration in Gemini Developer Mode Authentication is the first compatibility path. DCR is intentionally not implemented; if the UI requires it, stop and review. Google guide: https://developers.google.com/connected-apps/mcp/dev-mode/usage and https://developers.google.com/connected-apps/mcp/oauth.

Existing verified Party Owner session is used only for the HTML consent and revoke-all pages. No Party session authorizes MCP. Consent is explicit and single-use, origin-checked, bound to a hashed nonce and the original request; codes expire after 2 minutes; opaque bearer tokens expire after 15 minutes. Store only SHA-256 hashes of nonce, code, and token, not their raw values. Token exchange is a single conditional SQL update; replay is denied. Resource, scope, client, Owner and exact redirect binding. No refresh or silent reauthorization. Revocation endpoint and Owner disconnect page. MCP accepts bearer authentication only and offers one fixed synthetic read tool with a different marker from stage 1.

Fail-closed configuration: production only, explicit PENNYCORE_MCP_DEMO_ENABLED=1, PENNYCORE_MCP_DEMO_REDIRECT_URIS (comma-separated exact app-specific Google callback URLs, max six, no wildcards), PENNYCORE_MCP_DEMO_DB_URL (a **separate** synthetic authorization database and restricted runtime role), existing PENNYCORE_OWNER_ACCOUNT_ID. Never use NEXUS_MEMORY_DATABASE_URL, NEXUS_MEMORY_KEY or Party DATABASE_URL for the OAuth store. No schema changes to existing databases. Apply db/pennycore-oauth-demo/001_grants.sql only to a newly approved isolated database. The protected resource and issuer metadata URLs are mapped by Vercel rewrites; verify actual HTTP routing before enabling. No credentials committed. Verify exact callback in Gemini Authentication panel before configuration, and verify the client registration method works. No activation until synthetic database tests including concurrent code exchange, expiry, revocation, and authenticated Gemini live tool events pass. No real memory exposure in this prototype. No paid provider API calls. No automated browser tests. Future private-record selection and provider privacy approval remain separate gates.

Consent, token issuance and revocation are unavailable (503) until the production-only enable flag, separate auth DB URL, and exact callback allowlist are all configured. No storage access occurs in this bootstrap state. The code rejects reuse of the exact existing Party or journal DB URL. The new isolated project is pennycore-oauth-demo (late-grass-92486193, main branch br-jolly-hat-bbx6wozs, database pennycore_oauth_demo, runtime role oauth_demo_runtime). ## Stage 2 automatic registration revision

The static public client has been retired in favor of RFC 7591 dynamic registration. Gemini may register only exact preconfigured callback URLs. Advertise `/register`, support client_secret_basic, client_secret_post and explicit public PKCE clients. Return generated credentials once over HTTPS; persist only a hash. Registration is capped at 64 active slots, each valid for 30 days; expired slots can be reused. A registration is not authorization: the existing Owner session, explicit consent, S256 PKCE, exact registered client, callback, resource and scope are required for token issuance. Tokens remain 15 minutes with no refresh; the registration response advertises authorization_code only even if the client requests refresh. Reauthentication is required after expiry. No change to real-memory access. Apply 002_dcr.sql only to the isolated OAuth demo database before production release. No new secrets or credentials need manual entry. The public demo is unchanged. Google actual registration and authorization must be confirmed by live events. See https://developers.google.com/connected-apps/mcp/oauth.

### Gemini long-state compatibility

Live authorization request inspection confirmed the expected client, exact callback, resource, scope and S256 PKCE; Gemini's opaque state was 1,111 characters, exceeding the initial 1,024 limit. Increase the bound to 4,096 in the authorization handler and isolated database constraint (003_oauth_state.sql). Preserve state verbatim and never log its value. No change to consent, PKCE, client authentication or real memory access.

## Public demo retirement

Owner requested retiring the original unauthenticated fixture to eliminate misleading Gemini fallback. `/api/pennycore-mcp-demo-v1` now returns 410 for all methods. The separate authenticated synthetic endpoint is unchanged. Private multi-engine Owner tools are not public concierge routes.

### Browser consent form compatibility

Production request metadata confirmed successful authorization GET (200) followed by consent POST (403) on two separate attempts. Native HTML form submissions under `Referrer-Policy: no-referrer` serialize Origin as `null`, conflicting with our exact same-origin POST guard. Consent/disconnect HTML now uses `strict-origin` (only origin, no path or query). All other OAuth responses retain `no-referrer`; the same-origin requirement, nonce, Owner session, exact callback, PKCE and anti-framing checks remain enforced. Null and foreign Origin are still rejected. No real memory access is enabled.
